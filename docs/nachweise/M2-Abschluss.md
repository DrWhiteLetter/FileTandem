# M2 – Verbindungen und Dateibrowser abgeschlossen

Alle neun Items sind umgesetzt und jeweils separat committed. Profile, sicher gespeicherte Anmeldung, verifizierte SSH-Sitzungen, echter lokaler/SFTP-Browser, Listenbedienung, Dateiverwaltung und native Verbindungsansicht sind verbunden. SFTP-only läuft ohne Shell; keine automatische Verbindung beim Restaurieren einer Ansicht. Echte Transfers bleiben M3, SCP-Dateiverwaltung M4.

Abnahme am 07.10.2026 auf macOS arm64, Node 22.13.1, VS Code 1.140.0: Quality mit 31 Unit-Tests und zwei gerenderten React-Tests. Vier reale Auth- und fünf Host-Key-Integrationstests bestanden; zwei neue SFTP-only-Browser-/Credential-/Dateiverwaltungstests bestanden. Letztere prüfen echte Passwort-/verschlüsselte-Key-Anmeldung, gespeicherte Anmeldung/Reconnect, stat/readdir, Unicode/Sonderzeichen, mkdir/rename-Konflikte, chmod und rekursives Löschen ohne Symlink-Zielzugriff.

Die private M2-VSIX trägt Version 0.0.2, damit eine bestehende M1-Installation aktualisiert werden kann. Die installierte VSIX wurde in zwei normalen, separat gestarteten VS-Code-Prozessen mit gemeinsamem temporärem Profil getestet. Dabei bleiben Profil/Favorit/Host-Key-Vertrauen erhalten; Commander lädt lokale und SFTP-only-Dateilisten ohne Workspace und trennt/verbindet erneut. Native lokale Rename-Konfliktprüfung und OS-Papierkorb bestanden. Der gewöhnliche Extension-Testmodus verwendet in dieser VS-Code-Version nur flüchtigen globalState und ist daher für diesen Persistenznachweis ungeeignet; der neue Test-Harness startet normale isolierte Fenster. Keine Benutzerprofile oder produktiven Server wurden verändert.

Bekannte Grenzen: Windows/Linux-Desktop, native visuelle Theme-/Zoom-/Restricted-Mode-Bedienmatrix und gehostete CI bleiben M6/offen. Windows-POSIX-chmod und lokale UNC-Authorities werden verweigert. 10.000 Einträge pro Ordner; Löschpläne maximal 10.000 Einträge/Tiefe 100. SFTP v3 bietet keine transaktionalen No-Follow-Pfadoperationen bei konkurrierenden externen Änderungen; vor einzelnen Löschschritten werden Typ/Eltern erneut geprüft. Kein endgültiger Fallback bei Papierkorbfehler. Eigene temporäre Papierkorb-Testordner können im OS-Papierkorb verbleiben.

# M0-06 – Echtes SCP nachweisen

Datum: 7. Oktober 2026. Zugehöriger Commit: `feat(M0-06): prove legacy SCP transfers and GNU listing` (dieser Nachweis gehört zum Implementierungscommit).

**Ergebnis: bestanden.** Ein eigener minimaler SCP-Sender/Empfänger über SSH-Exec lädt Dateien mit identischen SHA-256-Hashes hoch und herunter. Das SFTP-Subsystem ist auf dem geprüften Server tatsächlich deaktiviert. GNU-Verzeichnisauflistung, Leerzeichen, Quotes und Shell-Sonderzeichen sind geprüft. Serveranforderungen und unsichere Namen stehen unten.

## Umsetzung

- `src/adapters/scp/transfer.js`: `transferScp(session, { direction, localPath, remotePath, signal?, onProgress?, timeout? })`. Genau eine reguläre Datei auf einer bereits durch `connectSsh` verifizierten Sitzung; Ergebnis `{ bytes, sha256 }`. Die Sitzung wird immer geschlossen. Keine SFTP-Anfrage und keine lokale SCP-CLI im Adapter.
- SSH-Exec ohne PTY: Upload mit `scp -t -- <Pfad>`, Download mit `scp -f -- <Pfad>`. SHA-256 läuft über die Datei-Bytes; lokale FileHandle-Reads/Writes und Channel-Writes erfolgen schrittweise, maximal 64 KiB. Write-Callbacks und sequentielle Reads begrenzen vorausgesendete Daten. Kein Ganzdateipuffer.
- `protocol.js`: SCP-C-Header, exakter angeforderter Basename, Oktalmodus, ganzzahlige Größe und Dateilimit; positive ACKs sowie Fehlerantworten; exakte Datenlänge, Abschlussmarker und kein nachfolgender zweiter Datensatz. UTF-8 wird strikt dekodiert. Der Reader verarbeitet fragmentierte und zusammengefasste SSH-Pakete, auch mit binären Kontrollbytes im Dateiinhalt.
- `exec.js`: gesamtes Zeitlimit (standardmäßig 30 Sekunden, zulässig 100 ms bis 5 Minuten), AbortSignal, begrenztes stderr (erste 8 KiB) und erfolgreicher Exitstatus erforderlich. Alle Verbindungen laufen über die bestehende Host-Key-Factory. Abbruch/Fehler beendet Exec und SSH; nach maximal einer Sekunde erzwingt die SSH-Sitzung das Schließen. Gepufferte Readable-Daten werden beim Aufräumen verworfen; der tatsächliche Channel-Close und SSH-Close werden abgewartet. Die Tests zeigten, dass ssh2s `destroy()` allein weder sein Node-`destroyed`-Flag setzt noch einen noch nicht gelesenen Kanal vollständig abschließt. Die Abnahme prüft deshalb echte Close-Ereignisse.
- Lokale Downloadziele mit `wx`, Modus 0600. Remote-Uploadziele mit POSIX-Shell-`noclobber` vor dem SCP-Sink reservieren; umask 077 und SCP-Modus 0600. Vorhandene reguläre Dateien bleiben erhalten. Keine automatische Löschung fremder Ziele.
- `list.js`: `listScp(session, { path, signal?, timeout? })`. Probe auf vorhandenes `scp`, GNU find/coreutils; verständliche Ablehnung bei fehlenden Werkzeugen. GNU `find -P`, eine Ebene, `LC_ALL=C`, sechs NUL-getrennte Felder: Name, Typ, Größe, Änderungszeit, Oktalmodus, Symlinkziel. Kein `ls -l`-Parsing. Strikte UTF-8-/Metadatenvalidierung; nicht transferierbare Namen und Symlinks bleiben als solche sichtbar.

## Serverprofil und Namen

Getestet: Linux/OpenSSH mit POSIX-kompatibler Shell, ausführbarem `scp`, GNU findutils/coreutils und `grep` im PATH. Dateien/Ordner müssen für den angemeldeten Benutzer zugänglich sein. SSH-Exec muss erlaubt sein. Kein VS Code Server und keine Shell für SFTP selbst erforderlich; **dieser SCP-Weg** benötigt aber Exec/Shell. Der SFTP-only-Server ist daher für SCP ungeeignet. Keine automatische Umschaltung auf SFTP oder eine CLI.

Alle Remote-Pfade sind absolute POSIX-Pfade und werden als ein einzelnes Shell-Argument mit Single-Quote-Escaping übergeben; `--` verhindert Optionen aus Pfaden. Quotes, Leerzeichen, Unicode, Dollarzeichen, Backticks, Semikolon und Wildcards bleiben literal. Der Testname enthält tatsächlich `$(touch INJECTION)` und Backticks; die entsprechenden Marker werden nicht erzeugt.

Früh abgewiesen werden ASCII-Steuerzeichen (inklusive LF/CR/NUL), DEL, Backslash, leere oder `.`/`..`-Pfadkomponenten, relative Pfade, doppelte/trailing Slashes und nicht verlustfrei UTF-8-kodierbare Strings. Basenames höchstens 255 UTF-8-Bytes, Pfade höchstens 4096 Bytes. Downloadheader müssen genau den erwarteten Basename nennen; fremde Namen, Slash/Traversal und Directory-/Timestamp-Records sind kein unterstützter Weg. Die NUL-Verzeichnisliste kann vorhandene Namen mit Zeilenumbrüchen darstellen, markiert sie aber `transferable: false`. SFTP ist die Alternative für solche Namen. BSD/macOS-, BusyBox-, Windows-SCP-Server und andere Shell-/Toolprofile sind nicht zugesagt.

## Umgebung und Reproduktion

macOS 26.6.2 / Darwin 25.6.0, Apple Silicon arm64, Node.js 22.13.1, npm 10.9.2, VS Code Desktop 1.140.0, ssh2 1.17.0. Separate Colima-VM `xscp`, Docker Engine 29.5.2, unveränderte M0-03-Fixtures mit Debian 12 / OpenSSH 9.2p1. Host-/Clientkeys Ed25519. Keine Tests gegen produktive Server oder persönliche Dateien.

```sh
colima start xscp --activate=false
export XSCP_DOCKER_CONTEXT=colima-xscp
npm run fixtures:start
npm run test:scp
npm run check
VSCODE_TEST_EXECUTABLE="/Applications/Visual Studio Code.app/Contents/MacOS/Code" npm test
npm run fixtures:stop
colima stop xscp
```

Test-Trust vergleicht vor Zustimmung den vollständigen Server-Key mit dem kontrollierten öffentlichen Fixture-Key. Persönlicher VS-Code-Trust bleibt unverändert. Testdaten liegen in einem eigenen lokalen Tempordner sowie UUID-benannten `/data`-Pfaden und werden im Test-Finally entfernt.

## Grenzen des Nachweises

Minimaler Einzeldatei-Prototyp: höchstens 1 GiB pro Datei, 4096 Bytes pro SCP-Zeile, 1 MiB pro Verzeichnisliste. Keine rekursiven SCP-Records, Timestamp-/Rechteerhaltung, Queue, Oberfläche oder Wiederaufnahme. M4 härtet den Parser weiter (Fuzzing, umfassende negative Serverantworten) und integriert Browsing/Dateioperationen/Finalisierung. Symlinkziele werden angezeigt, aber eine vollständige Transfer-Symlink-Policy und sicheres Navigieren sind noch nicht umgesetzt.

Die Uploadreservierung ist keine atomare Veröffentlichung und schützt nicht vor einem parallel verändernden Serverprozess. Bestehende Ziele bei Rennen, Symlinks oder speziellen Dateien sind noch nicht umfassend geprüft. Nach Fehler/Abbruch können eigene leere/partielle Ziele verbleiben; Test-Finally räumt nur seine eigenen Pfade auf. Keine fsync-/Remote-Durability-Garantie. Lokale Quellgröße wird geprüft, gleich große Inhaltsänderungen werden noch nicht erkannt. Fortschritt zählt übertragene Bytes, nicht dauerhaft gespeicherte Bytes. Dateien über 4 GiB, fremde Serverprofile, Windows/Linux-Desktop und Ruhezustand wurden nicht geprüft.

Grundlagen: [OpenSSH-SCP-Implementierung 9.2p1](https://github.com/openssh/openssh-portable/blob/V_9_2_P1/scp.c), [OpenSSH scp und Legacy-Modus](https://man.openbsd.org/scp). Das Protokoll wird hier eigenständig implementiert; der Adapter startet keinen lokalen SCP-Prozess.

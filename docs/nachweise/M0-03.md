## Umsetzung und Zugänge

Dockerfile, Daemon-Konfiguration und Startskript unter `test/fixtures/ssh/`. `scripts/ssh-fixtures.mjs` stellt init/start/status/verify/stop/reset bereit. Die npm-Befehle sind in der [Fixture-Anleitung](../../test/fixtures/ssh/README.md) dokumentiert.

| Variante | Zugang | Getestete Grenze |
| --- | --- | --- |
| SFTP | `fixture@127.0.0.1:22220` | SFTP und Shell verfügbar |
| SFTP-only | `fixture@127.0.0.1:22221` | SFTP verfügbar; Shell-Marker nicht ausgeführt; `scp -O` abgewiesen |
| SCP ohne SFTP | `fixture@127.0.0.1:22222` | SFTP-Subsystem ausdrücklich abgewiesen; `scp -O` in beide Richtungen möglich |

Anmeldung ausschließlich mit dem generierten Ed25519-Testclient-Key. Jede Servervariante hat einen eigenen Host Key. Die kontrollierten Public Keys erzeugen die lokale `known_hosts`-Datei; `StrictHostKeyChecking yes` bleibt bei allen Tests aktiv. Ein anderer Testclient-Key wird auf jeder Variante konkret mit `Permission denied (publickey)` abgewiesen.

Die Container verwenden ein eigenes Docker-Bridge-Netzwerk, unprivilegierten Login-Benutzer, beschränkte Ressourcen, kein Forwarding und keine produktiven Dateimounts. Loopback-Bindings wurden sowohl mit Docker als auch mit `lsof` bestätigt: Listener ausschließlich auf `127.0.0.1:22220–22222`. Ausgehender Netzwerkzugriff ist auf dem normalen Bridge-Netz nicht gesperrt. Der erste Versuch mit einem internen Docker-Netz stellte die veröffentlichten Ports in dieser Colima-Umgebung nicht bereit; die geprüfte Endfassung verwendet das eigene normale Bridge-Netz.

## Prüfschritte und Ergebnisse

```sh
export XSCP_DOCKER_CONTEXT=colima-xscp
npm run fixtures:start
npm run fixtures:verify
npm run fixtures:stop
npm run fixtures:status
npm run fixtures:start
npm run fixtures:verify
npm run fixtures:reset
npm run fixtures:start
npm run fixtures:verify
npm run check
```

- Alle drei Zugänge nach Start erreichbar, nach Stop nicht mehr als Container vorhanden.
- Auf beiden SFTP-Varianten kleine Datei hoch- und herunterladen, bytegleich vergleichen, Probe entfernen: bestanden.
- Auf dem SCP-Server ist das SFTP-Subsystem nachweislich nicht vorhanden; Legacy-SCP mit explizitem `-O` lädt dieselbe kleine Probe in beide Richtungen bytegleich: bestanden. GNU-Werkzeuge verfügbar.
- SFTP-only führt den angeforderten Shell-Marker nicht aus und lehnt Legacy-SCP ab: bestanden.
- Falscher Clientkey auf allen Varianten konkret als Authentifizierungsfehler abgelehnt: bestanden.
- Stop/erneuter Start mit gleichem Clientkey: bestanden; Fixture-Prüfung erneut erfolgreich.
- Reset entfernt das generierte Runtime-Verzeichnis; nächster Start erzeugt einen anderen Clientkey und neue Hostidentitäten. Erneute Prüfung mit strikter Host-Key-Prüfung: bestanden.
- Remote Docker-Endpoint per `DOCKER_HOST=ssh://...` wird vor Daemon-Zugriff abgewiesen: bestanden.
- JavaScript-Syntaxprüfung und Extension-/Webview-Build: bestanden.

Der generierte Prüfbericht `test/fixtures/ssh/.runtime/verification.json` enthält tatsächliche Versionen, individuelle Host-Key-Fingerprints, Image-ID und Ergebnisse. Er bleibt lokales, ignoriertes Testmaterial. Kleine OpenSSH-Client-Roundtrips belegen die Fixtures; sie ersetzen keine späteren Tests der xScp-/ssh2-Adapter, Streaming/Abbruch oder des eigenen SCP-Parsers.

## Testkeys und VSIX

Testkeys werden beim Start erzeugt, nicht eingecheckt und nicht im Dockerfile hinterlegt. Client-Private-Keys werden nicht in Servercontainer eingebunden. Vom Debian-Paket während des Builds erzeugte Standard-Hostkeys werden im selben Build-Schritt entfernt; zur Laufzeit wird ausschließlich der individuelle Fixture-Key installiert.

- `.gitignore`: generierte `.runtime/` ignoriert; mittels `git check-ignore` geprüft.
- `.dockerignore`: `.runtime/` und Anleitung aus Build-Kontext ausgeschlossen; gebauter Kontext nur ca. 6 KiB.
- `.vscodeignore`: kompletter `test/`- und `scripts/`-Baum ausgeschlossen.
- VSIX-Dateiliste mit vorhandenen generierten Keys geprüft: keine Fixtures/Testkeys enthalten.
- Echte temporäre VSIX gebaut und als ZIP geprüft: keine `test/`-/`scripts/`-Einträge, keine Host-/Client-Key-Dateien und kein OpenSSH-Private-Key-Material enthalten.

```sh
npm exec --yes --package=@vscode/vsce -- vsce package \
  --no-dependencies --skip-license --allow-missing-repository \
  --no-rewrite-relative-links --out /tmp/xscp-m0-03.vsix
```

Dieses Paket ist nur eine lokale technische Packaging-Prüfung; Lizenz und öffentlicher Publisher bleiben gemäß Plan später zu klären. Keine Veröffentlichung.

## Zustand nach der Abnahme und Grenzen

Eigene Fixture-Container und eigenes Netzwerk entfernt; Colima-Profil `xscp` gestoppt. Das separate Profil, Image-Cache, generierte Testkeys und der lokale Prüfbericht bleiben für Folgetests erhalten. Homebrew stellt Colima, Lima und Docker bereit; kein Autostart-Service eingerichtet und Standard-Docker-Kontext weiterhin `default`. Der angebotene produktionsnahe Server wurde für M0-03 nicht verwendet.

Bisher macOS/Apple Silicon geprüft; Windows, Linux-Desktop und amd64 nicht ausgeführt. Das Basisimage unterstützt mehrere Architekturen, doch dies ersetzt keine Plattformprüfung. Der Docker-Build funktionierte mit dem Legacy-Builder; dessen Deprecation-Hinweis verlangt für zukünftige Docker-Versionen gegebenenfalls die Buildx-Komponente. Diese Fixtures sind reine SSH-Protokollumgebungen; insbesondere Forwarding ist deaktiviert. Ein Remote-SSH-/VS-Code-Server-Test wäre separat vorzubereiten und gehört weiterhin zur M0-02-Abnahme.

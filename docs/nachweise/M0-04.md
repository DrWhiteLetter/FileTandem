# M0-04 – Host-Key-Prüfung erproben

Datum: 7. Oktober 2026. Zugehöriger Commit: `feat(M0-04): enforce SSH host key verification` (dieser Nachweis gehört zum Implementierungscommit).

**Ergebnis: bestanden.** Unbekannte Schlüssel benötigen ausdrückliche Zustimmung; Ablehnung schließt die Verbindung. Tatsächlich geänderte Server-Keys werden auf allen drei Fixture-Varianten blockiert. Alle aktuellen SSH-Verbindungen verwenden dieselbe verpflichtende Prüfung.

## Umsetzung

- `ssh2` 1.17.0, exakt in npm-Manifest/Lockfile fixiert. Einzige Client-Erstellung und `connect`-Stelle unter `src/adapters/ssh/connect.js`. Die Factory akzeptiert keine Optionen für `hostVerifier`, `hostHash`, Transport-Sockets oder Algorithmusübersteuerungen. Fehlende Host-Key-Policy ist ein Fehler.
- `hostVerifier` erhält den binären öffentlichen Server-Key. Algorithmus wird mit ssh2 gelesen; SHA-256 wird über den SSH-Wire-Key berechnet, als OpenSSH-Base64 ohne Padding angezeigt. Vergleich erfolgt gegen den vollständigen gespeicherten Key, nicht nur gegen den Fingerprint.
- Native modale VS-Code-Warnung für unbekannte Keys: Host/Port, Algorithmus, SHA-256-Fingerprint, Hinweis auf unabhängigen Vergleich. Erster Button **Ablehnen**; nur **Vertrauen und verbinden** liefert Zustimmung. Escape/fehlende Entscheidung gilt als Ablehnung. Keine Trust-Entscheidung in der Webview.
- Public-Key-Trust-Records separat in `globalState`, versioniert und mit Host/Port identifiziert; keine Schlüssel/Passwörter der Client-Anmeldung, keine Sync-Registrierung. DNS wird normalisiert; unterschiedliche Ports und Host-Aliase bleiben getrennte Identitäten.
- Ungültige Trust-Daten, Speicherfehler, fehlender Dialog oder fehlerhafte Dialogantworten blockieren. Geänderte Keys erlauben keinen Zustimmungsdialog und überschreiben niemals das vorhandene Vertrauen.
- Entscheidungen desselben Endpoints werden innerhalb einer Store-Instanz serialisiert. Eine zweite Verbindung mit anderem Key kann eine erste Zustimmung nicht überschreiben.
- Verifikation vor Authentifizierung und Freigabe von SFTP-/Exec-Kanälen. Kein Client mit ungeschütztem Reconnect wird herausgegeben; Sitzungen bieten nur SFTP, Exec und Schließen. Abbruch und Zeitlimit schließen das Socket; nach Abbruch einer noch offenen Entscheidung wird eine verspätete Zustimmung nicht gespeichert.
- Command `xscp.verifySshHostKey`: lokaler, vertrauenswürdiger Extension Host; Host/Port/Benutzer und lokalen privaten Testkey auswählen, Host-Key prüfen, authentifizieren, Erfolg/Fingerprint lokal ausgeben und Verbindung schließen. Die UI-Probe unterstützt derzeit unverschlüsselte Key-Anmeldung; vollständige Authentifizierungsmatrix folgt in M0-07.

## Getestete Umgebung

macOS 26.6.2 / Darwin 25.6.0, Apple Silicon arm64, Node.js 22.13.1, npm 10.9.2, VS Code Desktop 1.140.0. Colima-Profil `xscp` 0.10.3, Docker Engine 29.5.2; die drei M0-03-Container verwenden OpenSSH 9.2p1 mit Ed25519-Host-/Clientkeys. Fingerprints werden unabhängig mit Desktop-OpenSSH 10.3p1 (`ssh-keygen -lf`) verglichen. Keine Verbindung zum produktionsnahen Testserver in dieser Abnahme.

## Prüfungen

```sh
colima start xscp --activate=false
export XSCP_DOCKER_CONTEXT=colima-xscp
npm run fixtures:start
npm run test:unit
npm run test:host-keys
npm run check
VSCODE_TEST_EXECUTABLE="/Applications/Visual Studio Code.app/Contents/MacOS/Code" npm test
```

Zusätzlich: Abbruch und Timeout bei offener Entscheidung, danach verspätete Zustimmung ohne Speicherung; sowie separat gebündelte SSH-Factory außerhalb von `node_modules`, die Ablehnung und erfolgreiche Authentifizierung ohne native Zusatzmodule demonstriert.

Der Key-Wechsel wird **im eigenen Container** mit `ssh-keygen` erzeugt und über SIGHUP des OpenSSH-Daemons aktiviert. Der neue empfangene Fingerprint muss genau zum rotierten Fixture-Key passen. Ein anschließender Container-Neustart stellt die unveränderten Originalkeys wieder her. Ownership-Labels werden vor Containeränderungen geprüft. Test-Trust ist rein lokal im Testprozess; das persönliche VS-Code-Trust-Store wird nicht verändert.

Die Tests machten die bisherige Fixture-EntryPoint-Konfiguration beim direkten Container-Neustart als nicht idempotent sichtbar. Sie wird jetzt vor jedem Start von einer unveränderten Basis kopiert. Änderungen an Host-Bind-Mount-Key-Dateien konnten durch VM-Dateisystem-Caching unvollständige/neue Dateiansichten liefern; die endgültige Testrotation erfolgt deshalb im Container-Dateisystem. Die finalen Tests benötigen keine Änderung der Desktop-Testkeys.

**Extension-Host-Smoke-Test bestanden:** Host-Bundle aktiviert, neuer Befehl registriert, bisheriger lokaler Dateinachweis und Webview-Tab weiterhin funktionsfähig. Native Dialogentscheidungen und Text werden über den tatsächlich verwendeten Dialogadapter mit Window-Testdouble geprüft; keine manuelle Klick-Abnahme des kompletten VS-Code-Dialogs in diesem Lauf.

## Packaging und Abnahmezustand

esbuild bündelt ssh2 und die nötigen JavaScript-Abhängigkeiten. Die optionalen Module `cpu-features` und `sshcrypto.node` werden nicht in die VSIX aufgenommen; ssh2 verwendet bei fehlenden optionalen Imports seine JS-/Node-Crypto-Implementierung. Gemeinsame Build-Optionen werden für den Host-Build und den isolierten Bundle-Smoke-Test verwendet. Drittanbieter-Lizenzen unter `THIRD_PARTY_NOTICES.md`.

Eine echte temporäre Test-VSIX wurde mit `vsce --no-dependencies` erzeugt und als ZIP geprüft: keine Fixtures, Client-/Host-Testkey-Dateien, `node_modules`, `.node`-Module oder Tests/Skripte enthalten. Generiertes privates Fixture-Key-Material wurde mit dem Paketinhalt abgeglichen. Die im ssh2-Quellcode enthaltenen Parser-Konstanten und öffentlichen Feature-Testdaten sind kein Fixture-Zugangsmaterial. Keine Veröffentlichung; Lizenz und endgültiger Publisher bleiben spätere Release-Aufgaben.

Nach Abnahme sind eigene Container/Netzwerk entfernt und Colima `xscp` gestoppt. Generierte Fixture-Identitäten bleiben für Folgetests verfügbar.

## Grenzen

Erstvertrauen basiert auf ausdrücklicher Nutzerentscheidung und unabhängigem Fingerprint-Vergleich (TOFU). Keine automatische Übernahme persönlicher OpenSSH-`known_hosts`, keine automatische Trust-Reparatur und noch kein UI-Verfahren zum bewussten Ersetzen/Löschen eines bestätigten Keys. DNS-Aliase werden absichtlich separat behandelt. Gleichzeitige Entscheidungen mehrerer VS-Code-Fenster, andere Host-Key-Typen, Windows/Linux-Desktop, weitere Auth-Verfahren und die vollständige Packaging-/Plattformmatrix sind noch nicht geprüft. Die Serialisierung gilt für die aktive Store-Instanz.

M0-04 testet Host-Key-Vertrauen; Streaming, Abbruch von Transfers und eigener SCP-Parser folgen erst in M0-05/M0-06. Der Remote-Workspace-Nachweis von M0-02 bleibt davon getrennt.

API-Grundlage: [ssh2 hostVerifier](https://github.com/mscdex/ssh2#client-methods). ssh2 akzeptiert Host Keys ohne `hostVerifier` standardmäßig automatisch; diese Konfiguration ist in xScp nicht erreichbar.
